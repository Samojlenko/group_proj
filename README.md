# Культурная карта Санкт-Петербурга

Интеллектуальный геопространственный веб-сервис культурных объектов
Центрального района Санкт-Петербурга (музеи, памятники, мемориалы, галереи).

Реализация по техническому заданию (`ТЗ.docx`), этапы — по §54.

## Стек

| Слой | Технологии |
|---|---|
| База данных | PostgreSQL 18 + PostGIS 3.6 + pgvector |
| Backend | Python 3.12, FastAPI, SQLAlchemy 2, GeoAlchemy2, Alembic |
| Frontend | React 18, TypeScript, Vite, Leaflet |
| AI | локальный open-source LLM через Ollama (qwen2.5:7b), эмбеддинги nomic-embed-text |
| Оркестровка | Docker Compose |

Архитектурные ограничения ТЗ:

* AI **не имеет доступа к SQL** и к схеме БД — на выходе только JSON, который
  валидируется Pydantic-моделью до каких-либо запросов (§23, §25).
* Все расстояния и пространственные отношения считает **только PostGIS**
  (`ST_DWithin`, KNN `<->`, `ST_Distance` по колонке `geography`) (§45).
* Интерфейс и документация — на русском языке.

Что умеет AI-помощник: список и поиск объектов по категориям/названию,
поиск рядом и в радиусе от точки, статистика по базе, рекомендации.
Запросы вне этой темы (погода, переводы, произвольные подсчёты) получают
внятный отказ с примерами штатных запросов — действие `other` в схеме,
а не бессмысленный список. Модель выбрана под железо: qwen2.5:7b (4,7 ГБ)
полностью помещается в 8 ГБ VRAM и разбирает типовой запрос за 0,5–1,3 с;
qwen2.5:14b не влезает в память и ушёл бы на CPU без выигрыша качества
для задачи «фраза → JSON».

## Требования

* Docker Desktop с включённым WSL 2.
* [Ollama](https://ollama.com) с моделями:

```bash
ollama pull qwen2.5:7b
ollama pull nomic-embed-text
```

По умолчанию сервис обращается к `http://host.docker.internal:11434`
(переменная `AI_BASE_URL` в `.env`).

## Быстрый старт

```bash
cp .env.example .env          # при необходимости поправьте пароли/адрес Ollama
docker compose up --build
```

При старте контейнеры:

1. `db` — PostgreSQL + PostGIS + pgvector, инициализация БД;
2. `backend` — применяет миграции Alembic и запускает Uvicorn,
   `GET /api/health` должен вернуть `{"status": "ok"}`;
3. `frontend` — сборка React + проксирование `/api` через nginx.

Документация Swagger: <http://localhost:8000/docs>.

## Данные (этап 2)

Данные реальные, из открытых источников (§8), каждый объект хранит
`source`/`source_id`:

* **OpenStreetMap** — выборка по полигону Центрального района
  (relation 1114902) через OSM API, тайлы закэшированы в `data/raw/osm/`;
* **Wikidata** — объекты нужных классов (музей/памятник/мемориал/галерея
  и их подклассы) с координатами; кэш `data/raw/wikidata/`;
* **Википедия (ru)** — лид статьи и категории как описание и ключевые слова.

Для Location Resolver (§26) дополнительно загружены именованные места:

* `data/processed/locations.json` — улицы и площади из OSM/Wikidata;
* `data/processed/landmarks.json` — ориентиры города (Эрмитаж, Исаакиевский
  собор, Петропавловская крепость, Невский проспект и др.) с синонимами.
  Без них запрос «рядом с Эрмитажем» не резолвился: в культурных объектах
  встречается только «Зимний дворец Петра I».

Резолвер дополнительно устойчив к падежным формам («Эрмитажем» → «Эрмитаж»,
«на Невском» → «Невский проспект») — сравнение по стемам слов.

Мемориальные доски (OSM `memorial=plaque`, ~193 шт.) сохранены в данных, но
помечены ключевым словом `мемориальная доска` и **скрыты по умолчанию** в UI
(фильтр «Показывать мемориальные доски», параметр `not_keyword` API) — так
категории остаются сбалансированными, а данные — полными (§8).

Скрипты (запускаются обычным Python, кэш делает их идемпотентными):

```bash
python scripts/fetch_osm.py          # тайлы OSM + полигон района
python scripts/fetch_wikidata.py     # сущности Wikidata
python scripts/enrich.py             # связка OSM<->Wikidata, улицы, статьи
python scripts/link_by_name.py       # связка по названию + проверка координатами
python scripts/fetch_locations.py    # именованные места для Location Resolver (§26)
python scripts/prepare_data.py       # чистка, дедупликация, фильтр по полигону
python scripts/import_data.py        # импорт в PostgreSQL (нужен доступ к БД)
python scripts/generate_embeddings.py# pgvector-эмбеддинги (§27, нужен Ollama)
```

Импорт и эмбеддинги удобно выполнять после `docker compose up`:

```bash
docker compose exec backend python scripts/import_data.py
docker compose exec backend python scripts/generate_embeddings.py
```

## API (основные endpoint'ы)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/health` | здоровье БД/PostGIS/pgvector/AI (§17) |
| GET | `/api/objects` | список с фильтрами (§15) |
| GET | `/api/objects/{id}` | карточка объекта (§33) |
| GET | `/api/objects/nearby` | ближайшие к точке (§11) |
| GET | `/api/objects/radius` | поиск в радиусе (§12) |
| GET | `/api/objects/{id}/distance/{other}` | расстояние между объектами (§13) |
| GET | `/api/objects/{id}/nearby` | «что рядом»: список + счётчики (§14) |
| GET | `/api/objects/search` | полнотекстовый поиск (§15) |
| GET | `/api/objects/geojson` | GeoJSON для карты (§16) |
| GET | `/api/categories` | категории (§6) |
| GET | `/api/statistics` | статистика (§36) |
| GET | `/api/district` | граница района (GeoJSON) |
| GET | `/api/analytics/heatmap` | плотность объектов (§37) |
| GET | `/api/analytics/density` | самые насыщенные зоны (§37) |
| GET | `/api/analytics/neighbours` | расстояния до соседей (§36) |
| POST | `/api/query` | естественный язык → структурированный запрос (§22–§25) |
| POST | `/api/recommend` | гибридные рекомендации: семантика + пространство + категория (§28–§30) |

Ограничения безопасности (§42): радиус ≤ `MAX_RADIUS_METERS`, `limit` ≤ `MAX_LIMIT`;
ошибки валидации → `400/422`, отсутствующий объект → `404`, недоступный AI → `503`.

## Возможности интерфейса

Интерфейс построен вокруг карты: технические детали (§-номера ТЗ, API-бейдж,
веса скоринга) скрыты от пользователя, статистика и второстепенные фильтры
свёрнуты по умолчанию.

* карта с категориями, тепловой картой плотности и границей района;
* один поиск в шапке: выпадающие подсказки с миниатюрами объектов (если есть
  картинка), категорией и адресом; стрелки/Enter/Esc, клик вне поля закрывает;
* «Что рядом с точкой?» — радиусный поиск кликом по карте;
* AI-помощник: поле ввода и примеры запросов; при пустом диалоге — примеры
  и история, после запроса — только результат;
* выделение результатов AI/поиска/радиуса на карте с расстояниями;
* карточка объекта и страница `/object/{id}`: ближайшие, похожие, радиусы
  500 м / 1 / 2 / 5 км;
* избранное (☆/★) с фильтром «Только избранное» — localStorage;
* скелетоны загрузки, кнопка повтора при ошибке, защита от гонок запросов.

Если Ollama недоступен, запросы разбираются шаблонами (rule-based fallback,
§53) и помечаются в ответе — сервис продолжает работать в обычном GIS-режиме.

## Структура

```
db/           Dockerfile + инициализация PostgreSQL/PostGIS
backend/      FastAPI-приложение (app/api, app/ai, app/spatial, app/models)
              alembic/ — миграции, tests/ — pytest
frontend/     React + TypeScript + Leaflet (src/components: карта, AI-панель, карточка)
scripts/      ETL: загрузка, очистка, импорт, эмбеддинги
data/         raw/ (кэш источников), processed/ (objects.json, locations.json)
docs/         дополнительные материалы
```

## Известные ограничения / TODO (§58)

* Внешний геокодер (§26) — реализован только fallback-каркас
  (`backend/app/ai/resolver.py`): эндпоинт внешнего сервиса в ТЗ не задан,
  поэтому автоматически не используется, чтобы не подставлять
  непроверенные координаты. Разрешение идёт по своей БД.
* Сессии диалога (§40) — `session_id` принимается, но не сохраняется.
* Эмбеддинги и семантическая часть рекомендаций работают только после
  запуска Ollama и `generate_embeddings.py`.

Статус этапов и журнал проверки реального запуска — в `docs/Этапы.md`.
