## 1. Что это за сервис

**Культурная карта Санкт-Петербурга** — веб-сервис с интерактивной картой
культурных объектов Центрального района: музеев, памятников, мемориалов и
галерей (474 объекта из открытых источников). Поверх карты работает
AI-помощник: он принимает вопрос на естественном языке («музеи рядом с
Эрмитажем», «что посмотреть сегодня, учитывая дождь») и превращает его
в строгий структурированный запрос, который исполняет сервис.

Ключевая архитектурная идея: **ИИ ничего не считает и не выдумывает**.
Модель только разбирает фразу в JSON, а все расстояния, фильтры и подборки
считает PostgreSQL + PostGIS; ответ дополнительно проверяется на честность
(числа из резюме сверяются с данными).

### Что умеет конечный пользователь

* смотреть 474 объекта на карте с фильтрами по категориям и атрибутам
  (сайт, описание, мемориальные доски, избранное);
* искать объекты по названию с выпадающими подсказками и фотографиями;
* измерять: «что рядом с точкой» (клик по карте), «в радиусе N метров»,
  «расстояние между двумя объектами», «сколько идти пешком»;
* спрашивать на естественном языке и получать результат на карте
  (подсветка, маршрут, метки);
* получать рекомендации по гибридному скорингу («похоже по описанию»,
  «рядом», «нужная категория» — вклад факторов виден);
* сохранять избранное и подборки (localStorage), открывать страницу объекта,
  смотреть статистику и тепловую карту плотности;
* включать слои городской инфраструктуры из OpenStreetMap — кафе ☕,
  туалеты 🚻, парковки 🅿️;
* видеть текущую погоду и подборки «под погоду» (в дождь — под крышей).

### Что умеет AI-помощник (интенты)

| Интент | Пример фразы | Что делает |
|---|---|---|
| `list` | «покажи галереи» | список по категориям с фильтрами |
| `search` | «найди музей Достоевского» | полнотекстовый поиск по названию/тексту |
| `nearby` | «что рядом с Эрмитажем» | ближайшие к названному месту |
| `radius_search` | «музеи в радиусе 1 км от Невского» | круг вокруг места/точки |
| `statistics` | «сколько всего музеев» | статистика по базе |
| `recommend` | «что посмотреть с детьми» | гибридные рекомендации (pgvector + PostGIS) |
| `distance` | «сколько идти от Эрмитажа до Дворцовой» | расстояние по прямой + время пешком |
| `compare` | «сравни Русский музей и Эрмитаж» | сравнение карточек двух объектов |
| `walk` | «построй прогулку на час от Дворцовой» | пеший маршрут с остановками на карте |
| `analytics` | «самый старый памятник» | экстремум по годам + следующие за ним |
| `surprise` | «удиви меня» | случайный «эффектный» объект (не повторяется в диалоге) |
| `taste` | «подбери похожее на моё избранное» | усреднение эмбеддингов избранного (pgvector) |
| `collection` | «собери топ-7 музеев и сохрани» | подборка с фото и описаниями |
| `quest` | «сделай квест по истории на 5 точек» | маршрут с вопросами из описаний |
| `amenities` | «где выпить кофе рядом с Эрмитажем» | кафе/туалеты/парковки из OSM с расстоянием |
| `weather` | «какая сегодня погода», «что посмотреть в дождь» | погода open-meteo + совет под погоду |
| `other` | «переведи на английский» | честный отказ с примерами штатных запросов |

Дополнительно: «открыто сейчас», «самый новый», уточнения в диалоге
(«а теперь только музеи», «в радиусе 500 метров», «покажи ещё»), многошаговые
вопросы через агент («какой музей самый старый и что рядом с ним»).

## 2. Стек и причины выбора

| Слой | Технология | Зачем |
|---|---|---|
| База данных | PostgreSQL 18 + PostGIS 3.6 + pgvector | PostGIS: индексированные пространственные операции (радиусы, ближайшие, расстояния) — всё считается в SQL (§45); pgvector: семантический поиск |
| Backend | Python 3.12, FastAPI, SQLAlchemy 2, Pydantic 2, Alembic | строгая валидация запросов/ответов, авто-документация `/docs`, миграции схемы |
| Frontend | React 18, TypeScript, Vite, Leaflet | лёгкая open-source карта без платных ключей, строгая типизация |
| AI | Ollama: qwen2.5:7b (разбор и резюме), nomic-embed-text (эмбеддинги) | локальная open-source модель (§4): 7b помещается в 8 ГБ VRAM и решает задачу «фраза → JSON»; облачные API запрещены ТЗ |
| Погода | open-meteo (REST, без ключей) | внешний источник только для погоды; при недоступности — честная деградация |
| Оркестровка | Docker Compose (3 контейнера) | одна команда поднимает весь стек; воспроизводимость |

**Три правила, которые держат архитектуру:**

1. LLM не имеет доступа к SQL и схеме БД: на выходе только JSON, который
   валидируется Pydantic-моделью **до** каких-либо запросов (§23, §25).
2. Все расстояния и пространственные отношения считает только PostGIS —
   данные не выгружаются в Python для сортировки (§45).
3. Ограничения и веса вынесены в переменные окружения, а не зашиты в код.

### Путь обычного запроса (пример: «музеи рядом с Эрмитажем»)

1. Фронтенд шлёт `POST /api/query/stream` (SSE) с текстом и координатами
   пользователя/карты, если они есть.
2. Backend нормализует текст и проверяет кэш разбора (§46).
3. Правила (`rules.py`) пытаются разобрать фразу детерминированно; если не
   вышло — модель через Ollama отвечает по JSON-схеме `StructuredQuery`
   (structured output), при ошибке — настраиваемое число повторов.
4. Резолвер (`resolver.py`) превращает «Эрмитажем» в координаты по своей
   таблице `locations` (365 мест: улицы, площади, ориентиры, синонимы).
5. `spatial/queries.py` выполняет параметризованный SQL: `ST_DWithin`,
   KNN `<->`, `ST_Distance` — фильтр, сортировка и расстояния считает PostGIS.
6. Ответ отдаётся кадром `result` (SSE), затем LLM-резюме печатается
   потоком кадров `token`… и всё закрывается кадром `done`. Числа резюме
   сверяются с фактами; при провале проверки уходит `reset` — клиент
   возвращает шаблонный текст.
7. Фронтенд подсвечивает результаты на карте, показывает список и резюме.

## 5. Данные и ETL

Данные реальные, из открытых источников (§8); каждый объект хранит
`source`/`source_id` (OSM, Wikidata, Википедия).

### Источники

* **OpenStreetMap** — граница Центрального района (relation 1114902) и
  тайлы OSM API (`/api/0.6/map`) сеткой по bbox; кэш `data/raw/osm/`.
* **Wikidata** — объекты нужных классов (музей/памятник/мемориал/галерея
  и подклассы) с координатами; кэш `data/raw/wikidata/`.
* **Википедия (ru)** — лид статьи и категории как описание и ключевые слова.
* **open-meteo** — только погода, в реальном времени (в базу не пишется).

### Конвейер (папка `scripts/`)

| № | Скрипт | Что делает |
|---|---|---|
| 1 | `fetch_wikidata.py` | объекты из Wikidata: SPARQL по району/городу (P131, P276), детали — wbgetentities |
| 2 | `fetch_osm.py` | граница района (relation 1114902) и тайлы OSM API сеткой по bbox |
| 3 | `prepare_data.py` | очистка, дедупликация (Wikidata — описания, OSM — часы/адрес), фильтр по полигону района |
| 4 | `enrich.py` | связка OSM ↔ Wikidata по явным тегам, подписи улиц для адресов, описания из Википедии |
| 5 | `link_by_name.py` | связка со статьями Википедии по названию (сущность ≤ 150 м, совпадение названий) |
| 6 | `import_data.py` | загрузка в PostgreSQL; **режим `amenities`** — только заведения, не трогает объекты и эмбеддинги |
| 7 | `export_geojson.py` | одноразовый экспорт objects.json → GeoJSON (для передачи/приёмки) |
| 8 | `fetch_locations.py` + `import_locations_only.py` | базовые места для резолвера (площади, проспекты) |
| 9 | `generate_embeddings.py` | векторы 768 измерений (name + description + themes + keywords), идемпотентно |
| 10 | `fetch_amenities.py` | кафе/туалеты/парковки из кэша OSM-тайлов → `data/processed/amenities.json` |
| — | `build_local_streets.py`, `_diag_dist.py` | улицы из локальных OSM-тайлов (дополняют `locations`); диагностика расстояний |

### Текущее наполнение базы

* **474 культурных объекта**: 310 мемориалов (в т.ч. 193 мемориальные
  доски — скрыты по умолчанию, иначе искажают статистику), 95 музеев,
  50 памятников, 19 галерей;
* **365 мест** в `locations` — улицы, площади, ориентиры с синонимами
  (нужны, чтобы понимать «рядом с Эрмитажем», «на Невском»);
* **1 граница района** (`districts`) — полигон Центрального района;
* **1103 заведения**: 783 кафе, 263 парковки, 57 туалетов (из OSM);
* **97 объектов с фотографиями** (Wikimedia Commons, изредка — image-тег OSM);
* **474 эмбеддинга** — по одному на каждый объект.

## 6. База данных

Образ: `postgis/postgis:18-3.6` + pgvector; при инициализации кластера

* `0001_initial` — базовые таблицы, PostGIS-колонки, pgvector;

## 8. Backend: пространственные запросы (`app/spatial/`)

Все пространственные вычисления — параметризованный SQL к PostGIS:

* `objects_nearby` / `objects_radius` — `ST_DWithin` по колонке `geography`,
  расстояние — `ST_Distance`, сортировка — KNN `<->` (индексы работают);
* `what_nearby` — «что рядом» со счётчиками по категориям;
* `search` — полнотекстовый поиск (tsvector + ILIKE) с сортировкой по
  расстоянию;
* `route` — «Прогулка»: жадный порядок остановок и перегоны в метрах;
* `analytics` — сетка плотности (heatmap), зоны, соседи;
* `amenities_near` / `amenities_geojson` — заведения OSM: радиус,
  категория, страницы (limit/offset).

## 9. AI-подсистема (`app/ai/`)

### 9.1. Конвейер разбора запроса

Порядок обработки фразы (каждый шаг дешевле следующего, §53):

1. **Нормализация и кэш** — текст схлопывается по пробелам, одинаковые
   формулировки отвечают из кэша (§46), не платя за модель дважды.
2. **Правила (`rules.py`)** — регулярные выражения детерминированно
   разбирают частые фразы; фан-действия и заведения/погода
   (`surprise`, `taste`, `collection`, `quest`, `amenities`, `weather`)
   перехватываются правилами **до** агента и модели — они надёжнее и быстрее.
3. **Модель** — Ollama получает JSON-схему `StructuredQuery` (structured
   output: форму гарантирует грамматика декодера), при неверном ответе —
   `AI_PARSE_RETRIES` повторов с текстом ошибки (§24).
4. **Валидация** — Pydantic-модель до каких-либо запросов (§25):
   неизвестная категория или неверный тип → повтор/отказ, а не мусор в SQL.
5. **Fallback** — если модель недоступна, работают только шаблоны;
   ответ помечается «запрос разобран шаблонами» (§53).
6. **Журнал «не понял»** (`unrecognized.py`) — отказ модели (`other`),
   спасение шаблонами (`fallback`) и провал разбора (`unparsed`) попадают
   в память процесса и видны через `GET /api/unrecognized` (идея 23).

Схема `StructuredQuery` описывает 17 действий (см. таблицу интентов),
категории с русскими синонимами, места, радиусы, флаги (`open_now`,
`has_website`…) и служебные поля (`amenity`, `advice`).

### 9.2. Резолвер мест (`resolver.py`)

«Эрмитажем» → координаты. Ищет по таблице `locations` (365 записей) с
учётом падежных форм (сравнение по стемам), опечаток (pg_trgm:
«двоцовая площадь» → «Дворцовая площадь»), латиницы и транслита
(«Hermitage» → «Эрмитаж»), синонимов («Русский музей» → «Михайловский
дворец», «Спас на крови» → «Храм Воскресения Христова»). «В 10 минутах
ходьбы» переводится в радиус 800 м (N × 80 м/мин). Внешний геокодер — только
fallback-каркас (эндпоинт в ТЗ не задан), разрешение идёт по своей БД.

### 9.3. Агент с function calling (`agent.py`)

Многошаговые вопросы («какой музей самый старый и что находится рядом с
ним») агент решает цепочкой инструментов — 8 функций: `find_objects`,
`find_place`, `distance`, `compare`, `walk`, `analytics`, `statistics`,
`recommend`. Модель только выбирает инструменты и аргументы; исполняет всё
сервис. Шаги видны в ответе («✦ Агент: 2 шага — аналитика по годам → поиск
объектов»). Любой сбой агента — тихий откат на обычный разбор
(`AI_AGENT_ENABLED=false` выключает).

### 9.4. Рекомендации (`recommend.py`)

Гибридный скоринг в SQL: `score = w_sem × семантика + w_spatial × близость +
w_cat × категория` (веса из настроек: 0.5 / 0.3 / 0.2). Семантика — косинусная
близость эмбеддингов через pgvector (`<=>`), близость — PostGIS, категория —
фильтр. Каждый объект несёт вклад факторов («почему эти», идея 17): фронт
рисует полоски «похоже по описанию 77% · рядом 23%».

### 9.5. Резюме и стриминг (`summary.py`)

Вместо шаблона «Объекты в радиусе…» помощник пишет короткое живое резюме
**строго по фактам ответа** (идея 16): факты собираются в JSON (до 5 объектов,
включая описания), модель пересказывает. Проверки честности: длина, отсутствие
служебного мусора (китайские вставки, слово «JSON»), **каждое число текста
обязано встречаться в фактах**. Провал любой проверки → тихо остаётся шаблон.
`POST /api/query/stream` печатает резюме потоком (SSE, идея 18): кадр
`result` (готовый ответ с шаблоном) → кадры `token`… → `done`; если собранный
текст не прошёл проверку — уходит `reset`, и клиент возвращает шаблон.
Резюме кэшируется по фактам (§46); для квестов не строится (раскрыло бы
ответы).

### 9.6. Диалог и уточнения (`sessions.py`, §40)

Сервер помнит предыдущий запрос диалога (LRU, 500 сессий, час жизни),
возвращает `session_id`, клиент присылает его со следующим вопросом.
Уточнения не требуют повторять фразу: «а теперь только музеи», «в радиусе
500 метров», «а теперь открытые», «покажи 2-й», «ещё» (листание через
offset), деиктика «рядом с этой точкой» (координаты карты).

### 9.7. Фан-режим (`fun.py`, `quest.py`)

* **«Удиви меня»** — случайный объект из пула 40 самых «эффектных» (фото +
  описание); в одном диалоге не повторяется, при пустом пуле условия
  ослабляются ступенями.
* **Профиль вкуса** — «подбери похожее на моё избранное»: сервер усредняет
  эмбеддинги до 50 избранных и ищет ближайшие по pgvector; сами избранные
  исключены из выдачи.
* **Подборки** — «собери топ-7 музеев и сохрани»: объекты с фото и
  содержательными описаниями, имя «Топ-7 музеев», живут на клиенте
  (localStorage), показываются на карте и добавляются в избранное пачкой.
* **Квесты** — маршрут тем же жадным алгоритмом, что прогулка, но остановки —
  объекты с русским описанием ≥ 40 символов; вопрос к объекту генерирует
  модель (с валидацией: без названия в тексте, без склейки алфавитов), при
  сбое — шаблон; на карте точки пронумерованы в порядке обхода.

### 9.8. Заведения OSM (`spatial/amenities.py`, идея 28)

Кафе/туалеты/парковки — отдельная таблица `amenities`, не смешиваются с
объектами культуры. Интент `amenities` («где выпить кофе рядом с
Эрмитажем») требует контекста («где», «рядом», «радиус», «покажи», «есть
ли…») — голое «Кафе» остаётся поиском. Расстояние считает PostGIS от точки
(место, точка на карте, геолокация), дефолтный радиус — 800 м, «покажи ещё»
листает через offset, в ответе — имя, адрес, часы, расстояние. Безымянные
кафе отсеяны при извлечении (32 из 815): «Кафе» без названия бесполезно.

### 9.9. Погода (`weather.py`, идея 29)

open-meteo без ключей: текущая температура, «днём +6…+11°», вероятность
осадков на ближайшие часы. WMO-коды переведены на русский; `is_rainy`
включает дождь, ливень, снег и грозу (по факту осадков, коду и вероятности
≥ 50%). Кэш в памяти 600 с, таймаут 8 с; при недоступности — данные
последнего удачного запроса, иначе честный 503. Интент `weather`:
«какая сегодня погода» → факты; «что посмотреть сегодня, учитывая дождь» →
совет: в дождь — крытые категории (музеи и галереи), в сухую — памятники.
Резюме погоды проверяется теми же гейтами, что и остальные.

### 9.10. Надёжность и деградация

* модель недоступна → шаблонный разбор и пометка в ответе (§53), сервис
  остаётся полностью работоспособным;
* холодный старт qwen (до ~17 с) скрыт фоновым прогревом при старте backend;
* фоновые таймауты и повторы настроены; `503` — только когда без модели
  совсем нельзя;
* ответ `other` — честный отказ с примерами штатных запросов;
* любой мусор модели в резюме отбрасывается — числа, CJK, JSON.

## 10. Frontend

### Компоненты

* `App.tsx` — состояние экрана: фильтры, поиск, фокус карты, слои, темы;
* `CulturalMap.tsx` — Leaflet-карта: маркеры категорий (цвета), подсветка
  результатов, радиус, тепловая карта, граница района, маршрут прогулки,
  слой заведений (эмодзи-метки ☕/🚻/🅿️ с попапами), тёмная/светлая
  подложка (Esri Gray Canvas меняется вместе с темой);
* `Sidebar.tsx` — категории, фильтры («Ещё фильтры» свёрнуты), статистика,
  список объектов; счётчики сходятся с видимыми маркерами;
* `AIPanel.tsx` — чат-панель: реплики, стриминг резюме с курсором, чипы
  уточнений, карточка «Удиви меня», подборки, квест, погодная карточка и
  бейдж текущей погоды, демо-сценарии;
* `ObjectCard.tsx` — карточка объекта (для карты) и `pages/ObjectPage.tsx` —
  страница `/object/{id}` (ближайшие, похожие, радиусы);
* `SearchBox.tsx` — поиск с подсказками (миниатюры, категория, адрес);
* `FactorBar.tsx` — полоски «почему эти» у рекомендаций.

### Библиотеки (`src/lib/`)

* `favorites.ts` — избранное в localStorage (`kmap.favorites`);
* `collections.ts` — сохранённые подборки (`kmap.collections`);
* `theme.ts` — тема (по умолчанию фирменная тёмная, выбор запоминается);
* `basemap.ts` — подложки карты в тон теме.

### Поведение

Слои заведений грузятся один раз при включении; ответ помощника сам включает
нужный слой, подсвечивает находки ореолом и центрирует карту. Избранное и
подборки — клиентские. Если Ollama недоступна, панель продолжает работать
на шаблонном разборе. Ошибки API показываются бейджем с кнопкой повтора;
есть защита от гонок запросов и скелетоны загрузки.

## 12. Запуск и конфигурация

```bash
cp .env.example .env            # при необходимости поправьте значения
docker compose up -d --build    # поднимет db + backend + frontend
# → http://localhost:3000       # интерфейс
# → http://localhost:8000/docs  # Swagger API
```

При первом старте база заполняется из `db/init/02-data.sql` автоматически.
Для AI-функций нужна Ollama на хосте: `ollama pull qwen2.5:7b` и
`ollama pull nomic-embed-text`. Без неё сервис работает в GIS-режиме
с шаблонным разбором запросов.

Основные переменные `.env` (все имеют значения по умолчанию):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `POSTGRES_USER/PASSWORD/DB` | `culturalfind` | доступ к БД |
| `BACKEND_PORT` / `FRONTEND_PORT` | `8000` / `3000` | порты хоста |
| `AI_BASE_URL` | `http://host.docker.internal:11434` | адрес Ollama |
| `AI_MODEL` / `EMBEDDING_MODEL` | `qwen2.5:7b` / `nomic-embed-text` | модели |
| `AI_ENABLED` | `true` | выключает AI целиком (`/api/query` → 503) |
| `AI_AGENT_ENABLED` | `true` | агент с function calling |
| `AI_SUMMARY_ENABLED` | `true` | LLM-резюме и стриминг |
| `AI_STRUCTURED_OUTPUT` | `true` | разбор по JSON-схеме |
| `AI_PARSE_RETRIES` | `1` | повторы при неверном ответе модели |
| `MAX_RADIUS_METERS` / `MAX_LIMIT` | `10000` / `100` | ограничения (§42) |
| `WEATHER_ENABLED` | `true` | погода open-meteo |
| `WEATHER_CACHE_SECONDS` | `600` | кэш погоды, секунды |
| `SCORE_WEIGHT_SEMANTIC/SPATIAL/CATEGORY` | `0.5` / `0.3` / `0.2` | веса скоринга (§28) |
| `LOG_LEVEL` | `INFO` | подробность логов |
| `GEOCODER_URL` | пусто | внешний геокодер (не используется) |
| `MAP_TILE_URL` | OSM tiles | тайлы карты |

Обновление данных: повторный запуск ETL-скриптов (раздел 5) и, при
необходимости, перегенерация дампа:
`docker compose exec -T db pg_dump -U culturalfind -d culturalfind --no-owner > db/init/02-data.sql`.
Важно: полный `import_data.py` пересоздаёт объекты и стирает эмбеддинги —
для заведений есть отдельный режим `amenities`, который их не трогает.

## 13. Известные ограничения

* Внешний геокодер (§26) — только fallback-каркас: разрешение мест идёт по
  своей БД (365 записей), чтобы не подставлять непроверенные координаты.
* Сессии диалога хранятся в памяти процесса (LRU, 500 диалогов, час жизни):
  после перезапуска backend контекст теряется; замена на Redis не меняет
  интерфейс.
* Эмбеддинги и семантика рекомендаций требуют Ollama и
  `generate_embeddings.py`.
* Заведения OSM — офлайн-выгрузка (`fetch_amenities.py` из кэша тайлов):
  сервис не ходит в OSM на каждый запрос, данные обновляются скриптом.
* Погода — внешний open-meteo: при недоступности отдаются данные последнего
  удачного запроса, иначе 503; остальной сервис работает как обычно.
* Картинки объектов грузятся с Wikimedia Commons — нужен доступ в интернет.
* Голосовой ввод (№19 плана апгрейда) сознательно не делался.
