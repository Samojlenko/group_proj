## Двенадцатый раунд: OSM-слой и погода — кафе, туалеты, парковки и прогноз (17.10.2026)

Этап H плана апгрейда (идеи 28–29): помощник отвечает на бытовые вопросы
прогулки — «где выпить кофе рядом с Эрмитажем» и «что посмотреть сегодня,
учитывая дождь», — не смешивая заведения с объектами культуры.

### Что сделано

* **Заведения из OSM (№28)** — кафе, туалеты и парковки лежат в отдельной
  таблице `amenities` (миграция 0003; `osm_id` — bigint: id в OSM бывают до
  10^10 и не влезают в int4). Извлечение — офлайн из кэшированных
  OSM-тайлов (`scripts/fetch_amenities.py`), импорт — режимом `amenities`
  в `import_data.py`: он не трогает `cultural_objects` и не стирает
  эмбеддинги. Безымянные кафе отсеиваются при извлечении (32 из 815):
  «Кафе» без названия в ответе бесполезно; туалетам и парковкам имя не
  нужно — у них фолбэк-подписи. Итог: **1103 заведения** (783 кафе,
  263 парковки, 57 туалетов).
* **API заведений** — `GET /api/amenities` (точка, радиус, категория,
  limit/offset — счётчики сходятся с видимыми) и `GET /api/amenities/geojson`
  для слоя на карте.
* **AI-интент `amenities`** — «где выпить кофе рядом с Эрмитажем» разбирается
  правилами до агента (§53): нужен контекст («где», «рядом», «радиус»,
  «покажи», «есть ли…») — голое «Кафе» остаётся поиском. Расстояние считает
  PostGIS от точки (Эрмитаж, точка на карте, геолокация), дефолтный радиус —
  800 м, «покажи ещё» листает через offset.
* **Погода open-meteo (№29)** — `app/ai/weather.py`: без ключей, кэш в памяти
  600 с, таймаут 8 с; при недоступности сервиса — устаревший кэш либо 503.
  WMO-коды переведены на русский, `is_rainy` включает дождь, ливень, снег и
  грозу. `GET /api/weather` отдаёт факты (температура, «днём +6…+11°»,
  вероятность осадков).
* **AI-интент `weather`** — «какая сегодня погода» → факты; «что посмотреть
  сегодня, учитывая дождь» → совет: в дождь — крытые категории (музеи и
  галереи), в сухую — памятники. Совет включается, когда погода действительно
  упомянута в запросе (`weather_advice_wanted()`).
* **Фронтенд** — тумблеры слоёв ☕/🚻/🅿️ над картой: эмодзи-метки с цветным
  контуром, попап с адресом и часами, данные грузятся один раз. Ответ
  помощника сам включает нужный слой, подсвечивает находки ореолом и
  центрирует карту; в панели — список заведений (имя, расстояние, адрес,
  часы), погодная карточка с иконкой и пометкой «возьмите зонт», бейдж-чип
  «Сейчас +9°, переменная облачность» в пустом диалоге, демо-чипы «☕ Кофе
  рядом с Эрмитажем» и «☔ Что посмотреть в дождь», чипы «Радиус …» и
  «Показать ещё» для заведений.

### Найдено вживую и исправлено

* «Кафе в радиусе 300 метров от Дворцовой площади» → 422: слово «радиус» не
  считалось контекстом заведений — добавлено в правило.
* qwen выдал в резюме китайскую вставку «預期的 JSON 格式…» (числа при этом
  сходились): `_BAD_SUMMARY_RE` отбрасывает такое резюме, а в SSE-потоке
  решение о `reset` теперь принимает `validate_summary`, а не только сверка
  чисел.
* SSE-поток падал на `Decimal` из SQL (`sem_score`, `spatial_score`,
  `distance_m` — numeric у psycopg; непоточный ответ спасал Pydantic):
  у кадра появился `_json_default`, рекомендации приводят служебные числа
  к float.
* Резюме погодных фактов упоминало места, которых нет в фактах, — в системный
  промпт добавлен прямой запрет.

## Одиннадцатый раунд: фан-режим — «Удиви меня», вкус, подборки, квесты (17.10.2026)

Этап G плана апгрейда: помощник научился удивлять, помнить вкус пользователя
и играть — при этом каждый ответ остаётся проверяемым (числа и названия
берутся только из данных сервиса, §4, §45).

### Что сделано

* **«Удиви меня» (№24)** — `app/ai/fun.py`: случайный объект из пула 40 самых
  «эффектных» (фото и описание, сортировка по длине текста). В одном диалоге
  не повторяется: показанные в прошлом ходу id исключаются (§40), а если пул
  пуст — условия ослабляются ступенями (фото+описание → описание → любой
  объект без повтора → повтор разрешён), чтобы «Удиви меня» не упиралось в
  пустоту. В панели — карточка с фото, описанием и кнопкой «Ещё раз».
* **Профиль вкуса (№25)** — «подбери похожее на моё избранное»: избранное
  приходит с клиента (`favorite_ids`), сервер усредняет эмбеддинги до 50
  избранных и ищет ближайшие по pgvector `<=>` — сами избранные из выдачи
  исключены. Нет избранного или нет эмбеддингов — 422 с подсказкой. В
  карточках видно «похоже по описанию N%», чип в панели появляется, только
  когда избранное непусто.
* **Подборки (№26)** — «собери топ-7 музеев и сохрани»: размер берётся из
  «топ-N» (по умолчанию 5, максимум 12), объекты — с фото и содержательными
  описаниями, имя — «Топ-7 музеев». Подборка живёт на клиенте (localStorage):
  показывается на карте, добавляется в избранное пачкой, удаляется; блок
  «Сохранённые подборки» — в пустом состоянии панели. Фраза со словом
  «сохрани» сохраняет подборку сразу, без лишнего клика.
* **Квесты (№27)** — «сделай квест по истории на 5 точек от Дворцовой
  площади»: `app/ai/quest.py` строит маршрут тем же жадным алгоритмом, что
  прогулку (§14), но остановки — только объекты с русским описанием ≥40
  символов (фильтр в SQL: среди ближайших N таких почти нет, из-за чего
  квест получался короче заказанного). Вопрос к объекту модель генерирует по
  описанию; вопрос с названием объекта, без опоры на текст, со склейкой
  алфавитов («Гдеlocated») или короче 12 символов отбрасывается — остаётся
  шаблон (год из описания или «О каком объекте идёт речь?»), квест работает
  и без модели (§53). Подсказка — первое предложение описания; служебный
  префикс ETL («Из-за ограничений на длину текста…») срезается. Резюме для
  квеста не строится: любое упоминание названий раскрыло бы ответы. На карте
  точки — нумерованные метки в порядке обхода; в панели ответы открываются
  кнопкой, есть счётчик «отвечено N из M».
* **Резюме (№16) обогащено**: в факты добавлено описание объекта (усечено до
  240 символов) — «эффектная подача» стала содержательной, числа из описаний
  легально становятся фактами; у подборок в фактах есть имя и размер.
* **Разбор фан-фраз — правилами до агента**: агент сводил «квест» к прогулке,
  а «подборку» — к списку (проверено вживую), поэтому четыре фан-действия
  (`surprise`, `taste`, `collection`, `quest`) детерминированно разбираются
  `rules.py` раньше function calling. Уточнено и правило вкуса: «покажи
  избранные музеи» — не профиль вкуса (избранное фильтруется на клиенте,
  фраза про вкус должна быть явной).

* `pytest` → **266 passed** (+40: разбор фан-фраз, ступени «Удиви меня»,

## Десятый раунд: надёжный разбор — JSON-схема, повторы, журнал «не понял» (16.10.2026)

Этап F плана апгрейда: разбор запроса моделью стал предсказуемым по форме
и наблюдаемым по сбоям — видно, чему помощника ещё учить.

### Что сделано

* **Structured output (№20)** — вместе с запросом разбора Ollama получает
  JSON-схему `StructuredQuery` (`format` — схема, а не просто «верни JSON»):
  форму ответа гарантирует грамматика декодера, а не послушность модели.
  Замер на живом qwen2.5:7b: схема не замедляет разбор (0,98 с против 0,87 с
  на той же фразе). Если сервер схемы не поддерживает — тихая деградация
  к простому JSON-режиму; `AI_STRUCTURED_OUTPUT=false` выключает принудительно.
* **Повторы разбора (№21)** — число повторов при неверном ответе модели
  настраивается (`AI_PARSE_RETRIES`, по умолчанию 1, максимум 3): модель
  получает конкретную ошибку схемы и шанс исправиться. Недоступность
  inference server по-прежнему сразу означает 503 — без ожидания повторов (§44).
* **Кэш разбора (№22)** — текст запроса нормализуется перед разбором (лишние
  пробелы и переводы строк схлопываются), поэтому одинаковые формулировки
  с разным оформлением дают один ключ кэша (§46) и не платят за модель дважды.
* **Журнал «не понял» (№23)** — `app/ai/unrecognized.py` + `GET /api/unrecognized`:
  последние 200 случаев, когда помощник спасовал, — «модель отказалась»
  (вопрос вне темы сервиса), «разбор шаблонами» (модель недоступна, §53),
  «не разобран» (422 после всех повторов). Формулировки видны через API
  (фильтр по поводу), полный текст каждой записи — в логе сервиса.

### Проверка (16.10.2026)

* `pytest` → **226 passed** (+16: схема и деградация при HTTP 400, нормализация
  запроса, повторы и их лимит, журнал и его эндпоинт, запись всех трёх
  поводов через API).
* Живой прогон (Ollama 0.31.1, qwen2.5:7b): схема принимается без деградации;

## Девятый раунд: живые ответы — резюме, «почему эти», стриминг (16.10.2026)

Этап E плана апгрейда: ответы помощника перестали быть сухими шаблонами —
LLM пишет короткое резюме строго по данным ответа, рекомендации объясняют
свой выбор, а текст печатается на глазах пользователя.

### Что сделано

* **LLM-резюме (№16)** — `backend/app/ai/summary.py`. Вместо шаблона
  «Объекты в радиусе…» — живой абзац: «Начни с Восточного крыла Главного
  штаба — он ближе всего…». Сервис собирает компактные факты из полей
  результата (первые объекты с расстояниями, счётчики, место, радиус) и
  просит модель пересказать их без выдумок. Числа резюме проверяются по
  фактам с допуском округления (±5% или 2 единицы для значений <1000,
  годы — точно), длина 12–400 символов; не прошло — тихо остаётся шаблон.
  Работает и на `/api/query` (обычный разбор и агент), и на `/api/recommend`
  с текстовым запросом; уточнения быстрым путём остаются мгновенными

## Седьмой раунд: агент с function calling (16.10.2026)

Этап C плана апгрейда: помощник перестал быть одиночным разбором — сложный
вопрос он решает цепочкой вызовов инструментов. Модель по-прежнему не видит
SQL (§23): она выбирает функции и аргументы, а всё исполняет сервис.

### Что сделано

* **Восемь инструментов** (`backend/app/ai/agent.py`, формат tools из
  Ollama/OpenAI API): `find_objects` (список / поиск / рядом / радиус /
  «открыто сейчас»), `find_place` (имя → координаты), `distance`, `compare`,
  `walk`, `analytics`, `statistics`, `recommend`. Аргументы инструментов
  проходят тот же `StructuredQuery` (§25) и исполняются тем же `_execute` —
  тексты и данные шагов не отличаются от одиночного разбора.
* **Цикл агента** — модель вызывает инструменты по одному (до 5 шагов),
  результаты уходят обратно компактным JSON (объекты, счётчики, маршрут; не
  больше 8 объектов на шаг). Составной вопрос «самый старый музей и что
  рядом с ним» — это `analytics` → `find_objects` с найденным музеем.
* **Самовосстановление** — ошибка инструмента («место не найдено», неверная
  категория, неполные аргументы) возвращается модели как результат вызова,
  и она исправляет аргументы; черновики в объяснение не попадают.
* **Ответ остаётся сервисным** — объяснение склеивается из шагов
  («Шаг 1: … Шаг 2: …»), `items` — из последнего результативного шага,
  маршрут прогулки и статистика переносятся как есть. Панель показывает
  «✦ Агент: 2 шага — аналитика по годам → поиск объектов», а «как понят
  запрос» — все вызовы (поле `agent_steps`).
* **Тихие откаты (§53)** — недоступность модели, отказ вызывать инструменты,
  ошибочные шаги: любой сбой означает обычный одиночный разбор, пользователь
  ничего не замечает. Выключается настройкой `AI_AGENT_ENABLED=false`.
* **Уточнения быстрым путём** — «а теперь только галереи» после ответа
  агента разбирается правилами, без вызовов модели; сессия помнит разбор
  последнего шага.

## Оценка AI-модели и внятный отказ (13.10.2026)

Архитектура: LLM — парсер, а не чат-бот. Пайплайн «текст → JSON по схеме
из 6 действий → Pydantic (§25) → SQL»; по §23 модель не видит БД и SQL.
Поэтому «любые» вопросы она не ответит — только вопросы о местах сервиса.

Замеры на qwen2.5:7b (4,7 ГБ, 100% GPU, RTX 5050 8 ГБ, контекст 4096):
штатные запросы карты разбираются за 0,5–1,3 с и отвечаются верно.
Более крупная модель не нужна: 14b в Q4 (~9 ГБ) не влезает в 8 ГБ VRAM
и ушёл бы на CPU (задержка выросла бы до 3–5 с), а задача «фраза → JSON»
не требует большой модели. Остаток VRAM нужен nomic-embed-text.

Дефект: на запросы вне схемы («погода», «переведи на английский»,
«сколько мест с тремя буквами А») модель притягивала запрос к
`list`/`statistics` и пользователь получал бессмысленный список 474
объектов вместо ответа.

Решение: добавлено действие `other` — модель честно отказывается,
а API отдаёт объяснение с примерами штатных запросов (200, `total=0`,
без фальшивого «ничего не найдено»).

Попутно исправлен баг валидации: промпт велит ставить `null` в
ненужные поля, но `categories: null` ронял валидацию → 422. Теперь
`null` нормализуется в `[]`.

Проверено вживую: погода / перевод / «2+2» / «3 буквы А» → отказ
`action=other`; «музеи в Центральном районе» → 95 объектов;
«музеи рядом с Дворцовой» → 34 объекта за 1,3 с.
`pytest` → **69 passed**, сборки фронтенда и backend чистые.

## Принятые решения

* Источники: OSM (boundary relation 1114902) + Wikidata + ru.Wikipedia;
  каждый объект хранит `source`/`source_id` (§8).
* Слияние дубликатов между источниками: радиус 60 м + схожесть названия;
  приоритет Wikidata для описаний, OSM — для эксплуатационных тегов.
* Мемориальные доски (`memorial=plaque`, 193 шт.) сохранены, помечены
  ключевым словом и скрыты по умолчанию — параметр `not_keyword` API
  и переключатель в UI (баланс категорий, §8).
* Внешний геокодер (§26) не используется автоматически: endpoint в ТЗ не
  задан, разрешение мест идёт по своей БД (`objects` → `locations`).
* Сессии диалога (§40): `session_id` принимается, но не сохраняется — TODO.
* PostgreSQL 18 (а не 17): ТЗ версию не фиксирует, а стабильный тег PostGIS
  с поддерживаемым PGDG-репозиторием — только `18-3.6`.
